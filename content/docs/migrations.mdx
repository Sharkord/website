Everything is in one SQLite file, `db.sqlite`, in the [data directory](/docs/data-dir). Migrations run automatically at startup, before the server accepts traffic.

## On Start

1. If migrations are pending, the database is snapshotted to `backups/`.
2. All pending migrations run in one transaction, with foreign keys off so table rebuilds do not cascade deletes.
3. The database is checked for orphaned rows, and the server starts.

There are no down migrations.

## Snapshots

```
backups/db.sqlite.1756108800000.before-0018_message_parent_reply_foreign_keys.sqlite
```

- Only taken when something is pending, once per pre-migration state.
- **Never deleted.** Prune them yourself.
- If the snapshot cannot be written (full disk), the server refuses to start.
- Database only, not uploads. Not a replacement for real backups.
- `server.backupDatabase=false` turns them off. Only do that if the database is huge and you back up yourself.

## When a Migration Fails

The transaction rolls back, so the database is unchanged. Reinstall the previous version, start it, and [open an issue](https://github.com/Sharkord/sharkord/issues) with the logged error and both versions. Never hand-edit the migrations table.

## Orphaned Rows

After migrating, the server logs `Database has N row(s) pointing at rows that do not exist` if it finds any. It still starts. A few are harmless. Large counts in `message_files`, `message_reactions` or `channel_read_states` right after an upgrade mean data was lost: stop and compare with the snapshot.

## Rolling Back

1. Stop the server.
2. Move `db.sqlite`, `db.sqlite-wal` and `db.sqlite-shm` aside.
3. Copy the snapshot from `backups/` to `db.sqlite`.
4. Put back the **old binary**. The new one would just migrate again.
5. Start it.

Running an older binary on a migrated database is not supported.
