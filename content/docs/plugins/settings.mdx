Register settings and they show up on your plugin's page in the server settings, where an admin can change them without touching code. Values are stored in the database and survive restarts. They are server-wide, not per user: see [`userData`](./data#per-user-storage) for that.

### Register

```ts
import type { PluginContext } from "@sharkord/plugin-sdk";

const onLoad = async (ctx: PluginContext) => {
  const settings = await ctx.settings.register([
    {
      key: "welcome-enabled",
      name: "Enable welcome messages",
      description: "Send a message when a user joins the server.",
      type: "boolean",
      defaultValue: true,
    },
    {
      key: "apiKey",
      name: "API key",
      type: "secret",
      defaultValue: "",
    },
    {
      key: "mode",
      name: "Mode",
      type: "enum",
      defaultValue: "fast",
      options: [
        { value: "fast", label: "Fast" },
        { value: "thorough", label: "Thorough" },
      ],
    },
  ] as const);

  const enabled = settings.get("welcome-enabled"); // boolean
  settings.set("welcome-enabled", false);
};
```

`register` is async: it reads the stored values, fills in defaults for keys it has not seen, writes them back, and hands you a typed accessor. Call it once, in `onLoad`, and keep the returned object.

<Alert type="info" title="Keep the `as const`">
  Without it the definitions widen to `string`, and `settings.get` loses both
  the checked key names and the type of what it returns.
</Alert>

### Types

| Type      | Renders as        | Notes                                                     |
| --------- | ----------------- | --------------------------------------------------------- |
| `string`  | Text field        |                                                           |
| `number`  | Number field      |                                                           |
| `boolean` | Toggle            |                                                           |
| `secret`  | Password field    | Write-only: never sent back to the client                 |
| `enum`    | Select            | Requires `options: [{ value, label }]`. Takes `multiple`  |
| `channel` | Channel picker    | Stores the channel id. `0` means none. Takes `multiple`   |
| `role`    | Role picker       | Stores the role id. `0` means none. Takes `multiple`      |

A definition takes `key`, `name`, `type`, `defaultValue`, an optional `description`, `options` for an enum, an optional `multiple` for an enum, channel or role (see [Picking Several](#picking-several)), and an optional `noneLabel` for what an empty picker shows. `key` is how you read the value back and how it is stored, so keep it stable across versions.

`secret` is the type for API keys and tokens. An admin can replace one but not read it back, and the value never leaves the server. Your plugin reads it normally with `get`.

### Channels and Roles

A log channel, a welcome channel, a moderator role: most plugins need to point at something on the server, and an id typed into a `number` field is an id nobody can find. `channel` and `role` render a dropdown of the server's channels or roles instead, and store the id of the one picked.

```ts
const settings = await ctx.settings.register([
  { key: "logChannel", name: "Log channel", type: "channel", defaultValue: 0 },
  { key: "modRole", name: "Moderator role", type: "role", defaultValue: 0 },
] as const);

ctx.events.on("user:banned", async ({ userId, reason }) => {
  const channelId = settings.get("logChannel"); // number

  if (channelId === 0) return;

  const channel = await ctx.channels.get(channelId);

  if (!channel) return;

  await ctx.messages.send(channelId, `<p>User ${userId} was banned: ${reason}</p>`);
});
```

Use `0` as the default: it means nothing is picked, and is always accepted. The picker starts with a **None** item that stores `0`, so an admin can clear a channel or role they picked earlier. Set `noneLabel` to name that item after what it means for your plugin, such as `noneLabel: "Don't log"`. When an admin saves, the server checks the channel or role exists and refuses one that does not, and a direct message channel is never offered or accepted.

That check only happens on save. A channel or role deleted afterwards leaves its old id in the setting, so look it up with `ctx.channels.get` or `ctx.roles.get` before using it, as above, or watch `channel:deleted` and `role:deleted`.

### Picking Several

Add `multiple: true` to an `enum`, `channel` or `role` setting and it renders as a dropdown of checkboxes instead, storing a list of the picked values. Use `[]` as the default: it means nothing is picked. The dropdown shows **None** while the list is empty, or your `noneLabel` if you set one.

```ts
const settings = await ctx.settings.register([
  {
    key: "watchedChannels",
    name: "Watched channels",
    type: "channel",
    multiple: true,
    defaultValue: [],
  },
  {
    key: "pingRoles",
    name: "Ping roles",
    type: "role",
    multiple: true,
    defaultValue: [],
  },
  {
    key: "tags",
    name: "Tags",
    type: "enum",
    multiple: true,
    defaultValue: ["bug"],
    options: [
      { value: "bug", label: "Bug" },
      { value: "feature", label: "Feature" },
    ],
  },
] as const);

settings.get("watchedChannels"); // number[]
settings.get("tags"); // string[]
```

Every item in the list is validated like a single value would be: each channel or role has to exist when an admin saves, and each enum value has to be one of the `options`. A list holds at most 100 items. `multiple` is ignored on the other types.

### Reading and Writing

`get` and `set` are **synchronous**. `get` reads the value from memory and always returns something, since a key an admin never saved falls back to its `defaultValue`. `set` updates it and persists in the background, so there is nothing to await.

```ts
const channelId = settings.get("welcome-channel-id"); // number
settings.set("welcome-channel-id", 42);
```

`set` on a key you never registered, or with a value of the wrong type, is ignored and logged as an error in the plugin's log.

### Reacting to Changes

An admin editing a value in the interface does not go through your `set`, so watch the [event](./events) instead:

```ts
ctx.events.on("setting:set", ({ key, value }) => {
  if (key !== "welcome-enabled") return;

  ctx.logger.log("welcome messages are now", value);
});
```

The event is scoped to your own plugin, so you never see another plugin's settings, but you do see your own writes as well as an admin's.

### Notes

- Values written from the interface are validated against your definition: a `number` setting cannot be set to a string, an `enum` cannot be set to a value outside its `options`, a `channel` or `role` setting cannot be set to an id that does not exist, and a `multiple` setting only takes a list.
- Settings are cleared from memory when the plugin unloads and reloaded from the database on the next `register`. The stored values are not deleted when a plugin is disabled, only when it is removed.
- Anything an admin can read in the interface is not a secret from admins. `secret` settings are hidden from the form, but a plugin running in the server process can do whatever it likes with them. See [Security](./security).
